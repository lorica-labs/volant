Volant is measured on three real workloads, each run by a recipe in the repository. Every figure on this page comes from those recipes.

On four Ansible Galaxy roles (`geerlingguy.security`, `nginx`, `git` and `pip`) applied to two Ubuntu 24.04 hosts that had already converged, Volant finishes in 0.529 s where ansible-core 2.19.12 with `pipelining = True` takes 26.435 s, a ratio of 49.97. On the official k3s-ansible `site.yml`, against an installed cluster, Volant takes 23.477 s and the reference 50.519 s, a ratio of 2.15. Measured on 2026-09-27 with `just bench` and `just bench-k3s`, which reproduce these figures. They have not been measured again since. The third workload, a full `molecule test` of a Galaxy role, is described under [Molecule](#molecule).

The two ratios are far apart because the roles change nothing on a converged host, so most of the reference's time there goes to the machinery around each module, and Volant removes most of that. The k3s playbook restarts services and runs install scripts on every pass, and that work takes as long under either engine. [What is left](#what-is-left) breaks it down.

## Configuration

| | |
|---|---|
| Managed hosts | two Ubuntu 24.04 hosts, 4 cores each, on an overlay network |
| Controller | Ubuntu 26.04, 8 cores |
| Volant | release build of `e57fbe5` (`v0.1.0-alpha.7-74-ge57fbe5`), default settings: native modules on, one ssh connection per host, `--facts auto`, batching off |
| Reference | ansible-core 2.19.12, `pipelining = True`, `forks` left at its default of 5, every other setting at its default |
| Roles workload | `geerlingguy.security` 3.0.2, `geerlingguy.nginx` 3.3.1, `geerlingguy.git` 3.0.1 and `geerlingguy.pip` 3.1.2 in one play, `become: true`, facts gathered, 56 tasks per host |
| k3s workload | the k3s-ansible playbooks at a pinned commit, k3s v1.31.12+k3s1, one server and one agent, the cluster installed first by a pass of the reference |
| Passes | one untimed warm-up pass per engine, then three timed passes of each, median reported |

Every timed pass has its `PLAY RECAP` compared with the first one, across both engines. A difference would mean the engines did different work, and the recipe would fail. On the roles every pass ended on `ok=28 changed=0 skipped=28` per host. On k3s every pass ended on `ok=34 changed=2 skipped=69` for the server and `ok=19 changed=3 skipped=54` for the agent. The `changed` tasks are the real work described under [What is left](#what-is-left).

The individual passes:

| Workload | Volant (s) | ansible-core (s) |
|---|---|---|
| Four Galaxy roles | 0.530, 0.529, 0.524 | 26.408, 26.438, 26.435 |
| k3s-ansible | 24.150, 23.448, 23.477 | 51.121, 50.519, 50.505 |

## Reproducing the figures

Both recipes build Volant in release mode, run against the hosts you name, and print the medians and the ratio. The controller needs ansible-core 2.19.12 installed with `uv tool install`, and the account on the hosts needs `sudo` without a password.

```sh
VOLANT_TARGET_HOST=host1 VOLANT_SECOND_HOST=host2 just bench 3
VOLANT_TARGET_HOST=host1 VOLANT_SECOND_HOST=host2 just bench-k3s 3
```

<Aside type="caution">
Both recipes change the hosts they run on. `just bench` installs the four roles' packages and configuration. `just bench-k3s` installs k3s, measures, then removes it. Use machines you can wipe.
</Aside>

Every timed Volant pass also writes its profile through `VOLANT_PROFILE_JSON`, under `target/bench/`, so a surprising number can be traced to the task that caused it. The tables below come from those files.

## Where the time went

Times are per host, from the median pass of 2026-09-27. The same workloads measured on 2026-09-24, before the native modules, took 12.66 s for the roles (reference 26.23 s) and 37.53 s for k3s (reference 50.19 s). [Decision record 0008](/docs/decisions/0008-native-modules-and-speed/) has the profile of that day.

## What is left

On k3s most of Volant's 23.5 seconds is work the playbook asks for:

- the restarts of the k3s service, about 8.3 seconds on the server and 4.8 on the agent, spent in `systemctl` and k3s itself;
- the k3s install script, about 1.4 to 1.5 seconds per host;
- 13 `command` tasks, such as `k3s --version`, about 3.1 seconds across both hosts.

Both engines pay for these the same way, because they are processes running on the host.

Two steps are held back by what the reference itself does:

- `service_facts` runs the commands ansible-core runs (`systemctl list-unit-files`, `service --status-all` and one `systemctl show` per unit) so that its answer is the same. The native module runs them side by side where the reference runs them one after the other, and they still make up most of its 2.4 seconds. It cannot go below them while it reads the same sources.
- The playbook's `apt` task sets `update_cache` without `cache_valid_time`, so the reference runs `apt-get update` on every pass. When this was measured, the native `apt` only answered a task with nothing to do, so this one went to the Python module, and the cache refresh is most of its 2.2 seconds. Since 2026-10-25 the native `apt` runs the update itself ([#879](https://github.com/lorica-labs/volant/pull/879)).

Those two steps together cost 4.5 to 4.7 seconds per host. Making them faster would mean reading other sources than the reference reads, and that decision is left to a later release.

## Molecule

`molecule test` runs the whole test sequence of a role. It removes any container left from an earlier run, checks the syntax, creates a container, applies the role (converge), applies it a second time to check that nothing changes (idempotence), and removes the container. Molecule starts `ansible-playbook` for each of these playbooks, so with Volant's `ansible-playbook` first on `PATH` the whole sequence runs under Volant, with no change to the role or to Molecule.

On `geerlingguy.nginx` with the docker driver, a full `molecule test` takes 60.349 s under Volant and 96.102 s under ansible-core 2.19.12, a ratio of 1.59. Both engines report the same `PLAY RECAP` lines on every pass. Measured on 2026-11-08 with `just bench-molecule 5`.

### Configuration of the Molecule workload

| | |
|---|---|
| Role | `geerlingguy.nginx` at commit `5ff0b23`, its `default` scenario: one Rocky Linux 9 container, 22 tasks |
| Image | `geerlingguy/docker-rockylinux9-ansible`, pinned by digest, pulled before the passes |
| Molecule | Molecule 26.11.0, molecule-plugins 26.11.0 and ansible-compat 26.11.0 in a Python 3.12 virtual environment, with `community.docker` 4.8.5 and `ansible.posix` 2.2.2 |
| Reference | ansible-core 2.19.12 from the same virtual environment, with the `ansible.cfg` Molecule writes (`forks = 50`) and every other setting at its default |
| Volant | release build of `da423e7` (`v0.1.0-alpha.13-265-gda423e78`), run through its `ansible-playbook` link, with `VOLANT_RUNTIME=system` |
| Machine | the controller of the other workloads (Ubuntu 26.04, 8 cores), which also runs Docker 29.1.3 and the container |
| Load | one-minute load average between 0.84 and 2.30 before and after every timed pass, in the same range for both engines |
| Passes | one untimed warm-up pass per engine, then five timed passes of each, alternating, median reported |

Every pass starts with no container and must end with none. On every pass converge ended on `ok=14 changed=8 skipped=8` and idempotence on `ok=12 changed=0 skipped=8`, under both engines.

|---|---|---|
| Create the container | 9.750 | 5.931 |
| Converge | 51.650 | 38.133 |

### What Volant does not change

Most of the time left under Volant is spent outside the engine:

- Converge installs nginx with `dnf`, which downloads packages from the Rocky Linux and EPEL mirrors. Idempotence runs the same tasks with nothing to install and takes 3.320 s, so most of converge's 38.133 s is the package installation. That time depends on the mirrors: one untimed warm-up of the reference failed when an EPEL mirror did not answer.
- Docker starts the container during create and stops and removes it during destroy. The engine only waits for it.
- A first `molecule test` on a new machine also pulls the image, 268,904,562 bytes. The recipe pulls it before the timed passes, so the figures above leave that download out. Its length depends on your network.

Two differences show in the logs and not in the recaps. Volant polls `async_status` sooner than ansible-core, so destroy can print one more `FAILED - RETRYING` line while it waits for docker. And the Volant passes set `VOLANT_RUNTIME=system`: without it, the implicit localhost runs the docker driver's modules under Volant's managed Python, which does not have the `docker` library, where ansible-core uses the Python of the virtual environment ([#1422](https://github.com/lorica-labs/volant/issues/1422)).

### Reproducing the Molecule figures

The recipe needs Docker and `uv` on the machine that runs it, and no other host. It builds Volant in release mode, installs the pinned versions under `target/molecule/`, fetches the role at its commit and pulls the image by digest:

```sh
just bench-molecule 5
```

The first argument is the number of timed passes per engine. Before each pass the recipe waits until no build or other `ansible-playbook` runs and the one-minute load average is under the second argument, 1.5 by default. It writes the medians and the load range to `target/molecule/logs/`, and fails if two passes report different `PLAY RECAP` lines or if a container named `instance` exists before or after a pass.

<Aside type="note">
These figures describe three workloads. Your own numbers depend on your network latency, on what your tasks do, on how many of them a native module covers, and on how many hosts you drive at once. `--profile` shows the split for your own run: see [Command line](/docs/reference/cli/#run-and-output).
</Aside>

[Decision record 0008](/docs/decisions/0008-native-modules-and-speed/) explains the choices behind these numbers and the options that were measured and dropped.
