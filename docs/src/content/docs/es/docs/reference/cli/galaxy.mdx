`volant galaxy` acepta los subcomandos y opciones de `ansible-galaxy` de ansible-core 2.19.12, así que los scripts y trabajos de CI escritos para él conservan sus líneas de comandos. Se está reescribiendo en Volant, sin el runtime de Python. Hoy lee las opciones y hace las comprobaciones que `ansible-galaxy` hace primero, y luego rechaza el subcomando hasta que llegue su versión nativa.

```sh
volant galaxy collection <download|init|build|publish|install|list|verify> [OPTIONS]
volant galaxy role <init|remove|delete|list|search|import|setup|info|install> [OPTIONS]
```

Todos los subcomandos aceptan `-s`/`--server`, `--token`/`--api-key`, `-c`/`--ignore-certs`, `--timeout` y `-v`, que se puede repetir. `collection download` y `collection install` aceptan además `--clear-response-cache` y `--no-cache`. Una opción desconocida, o un valor del tipo equivocado, sale con 2 e imprime el uso. `volant galaxy --version` imprime el bloque de versión de `ansible-galaxy`.

## Las primeras comprobaciones

Van antes de cualquier trabajo, con los mensajes y códigos de salida de `ansible-galaxy`:

| Caso | Mensaje | Salida |
|---|---|---|
| `collection install` con nombres y `-r` | `[ERROR]: The positional collection_name arg and --requirements-file are mutually exclusive.` | 1 |
| `collection install` o `download` sin ninguno de los dos | `[ERROR]: You must specify a collection name or a requirements file.` | 1 |
| `-r` nombra un archivo que no existe | `[ERROR]: The requirements file '<path>' does not exist.` | 1 |
| `role install` sin nombre ni `-r` | `[ERROR]: - you must specify a user/role name or a roles file` | 5 |
| `role install -r` con un archivo que no termina en `.yml` o `.yaml` | `[ERROR]: Invalid role requirements file, it must end with a .yml or .yaml extension` | 1 |
| `role list` sin ninguna ruta de roles existente | `[WARNING]: - the configured path <path> does not exist.` por cada ruta, y después `[ERROR]: - None of the provided paths were usable. Please specify a valid path with --roles-path` | 5 |

Cuando ninguna ruta de colecciones configurada está bajo el `PATH` de `collection install -p PATH`, el comando imprime primero el aviso de `ansible-galaxy`: `[WARNING]: The specified collections path '<PATH>' is not part of the configured Ansible collections paths '<paths>'. The installed collection will not be picked up in an Ansible run, unless within a playbook-adjacent collections directory.` El directorio `collections/` del runtime, que Volant añade al final de la ruta de colecciones, no aparece en `<paths>`.

## Instalar desde un tarball

`collection install` instala de forma nativa un tarball de colección: `volant galaxy collection install acme-demo-1.0.0.tar.gz -p DIR`. El nombre y la versión vienen del `MANIFEST.json` del tarball, no del nombre del archivo. La colección va bajo `DIR/ansible_collections/<namespace>/<name>`, o bajo la primera ruta de colecciones sin `-p`. Solo se escriben los archivos que lista `FILES.json`, cada uno comprobado antes contra su SHA-256. Un archivo queda en `0644`, o en `0755` cuando el archivo comprimido lo marca como ejecutable. Una entrada que acabaría fuera de la colección se rechaza, igual que un enlace que apunta fuera de ella. Una instalación que falla no deja ninguna colección a medio escribir. La salida, los mensajes y los códigos de salida son los de `ansible-galaxy`. Una colección ya instalada en la misma versión da `Nothing to do. All requested collections are already installed. If you want to reinstall them, consider using `--force`.`, y `--force` la vuelve a instalar sobre el árbol anterior. Cuando `PATH/ansible_collections` ya existe, el aviso de `-p` dice que la ruta `appears to be part of the pip Ansible package`, como lo dice `ansible-galaxy`.

Los directorios, las URL, git y las firmas se rechazan hasta que sean nativos: `[ERROR]: volant galaxy collection install from a directory, a URL or git is not supported yet`, o `with signatures`, salida 1.

## Instalar desde servidores Galaxy

`collection install` acepta también nombres, con un rango si hace falta: `demo.base`, `demo.base:1.0.0`, `"demo.base:>=1.0.0,<2.0.0"`, y las entradas de `-r`. Cada nombre se resuelve contra los servidores con sus dependencias, cada una en la versión más alta que cumple todos los rangos pedidos, retrocediendo cuando dos rangos chocan. Las versiones preliminares solo cuentan con `--pre` o cuando se nombran exactamente. Cada tarball se descarga, se comprueba contra el SHA-256 que da el servidor y se desempaqueta como arriba. Una colección instalada desde un servidor recibe también `ansible_collections/<namespace>.<name>-<version>.info/GALAXY.yml`, que anota su origen. Una colección ya instalada en una versión que encaja se conserva: `'<name>:<version>' is already installed, skipping.`

`-n` omite las dependencias, `-U` lleva las colecciones instaladas a la versión más nueva del rango, `-f` reinstala las colecciones pedidas y `--force-with-deps` también sus dependencias, `-i` sigue tras una instalación fallida con un aviso, y `--offline` no consulta ningún servidor. Cuando ningún conjunto de versiones cumple todos los rangos, el comando falla con el mensaje de `ansible-galaxy`, que lista los rangos y termina con una pista sobre `--pre`; los objetos de Python que `ansible-galaxy` imprime después de esa pista se omiten.

## Descargar para una instalación sin conexión

`collection download` resuelve las colecciones pedidas con sus dependencias, como `install`, y guarda cada tarball en la carpeta que nombra `-p`, `./collections` por defecto. Después escribe allí un `requirements.yml` que lista los tarballs por nombre de archivo, con sus versiones. En una máquina sin red, `volant galaxy collection install --offline -r requirements.yml` ejecutado desde esa carpeta los instala sin consultar ningún servidor. Los nombres de archivo se leen desde el directorio de trabajo, como los lee `ansible-galaxy`. `-n` deja fuera las dependencias, y `-r` y `--pre` funcionan como en `install`. Con `--offline`, un nombre que ningún tarball aporta, o una dependencia que no está instalada, falla con el mensaje del resolvedor.

## Servidores Galaxy

Los servidores vienen de `-s`, si no de `[galaxy] server_list` y de las secciones `[galaxy_server.<name>]` de `ansible.cfg`, si no de `GALAXY_SERVER`, `https://galaxy.ansible.com` por defecto. Cada variable `ANSIBLE_GALAXY_*` va antes que el archivo. Cada servidor acepta `url`, `token`, `validate_certs` y `timeout`. `--token` gana al token del archivo, `-c` desactiva la comprobación de certificados, y `--timeout` fija la espera, 60 segundos por defecto. Un servidor inalcanzable se salta con el aviso de `ansible-galaxy`, y se consulta el siguiente.

El token va en `Authorization: Token <token>` y nunca se imprime. Sin token se lee el archivo de token, `GALAXY_TOKEN_PATH`, por defecto `<ANSIBLE_HOME>/galaxy_token`, que se crea vacío con modo `0600` si falta. Los proxies vienen de `https_proxy`, `http_proxy`, `all_proxy` y `no_proxy`; a diferencia de `ansible-galaxy`, que elige la variable según el esquema de la URL, la primera que está definida se aplica a todas las URL. Las respuestas se guardan un día en `<ANSIBLE_HOME>/galaxy_cache/api.json`, el mismo archivo que usa `ansible-galaxy`. `--no-cache` lo deja de lado y `--clear-response-cache` lo vacía. `username`, `password` y `auth_url` no se leen.

## Archivos de requisitos

`-r` lee el archivo de requisitos como `ansible-galaxy`: `collections:` y `roles:` en un mismo archivo, o la antigua lista simple de roles, que solo acepta `role install`. Una entrada `include:` trae los roles de otro archivo, cuya ruta se toma desde el directorio de trabajo. Si `-r` se da dos veces, cuenta el último. Si el archivo no tiene ninguna entrada para el comando, `collection install` y `role install` imprimen `Skipping install, no requirements found` y salen con 0. `-vvv` imprime primero `Reading requirement file at '<path>'`. Un archivo mal formado falla con el mensaje de `ansible-galaxy`, salida 1: sin entradas, claves distintas de `collections` y `roles`, una entrada de rol sin `name` ni `src`, un nombre de colección que no es `namespace.name` y no apunta a nada, o un `type` desconocido.

## Subcomandos rechazados

Un subcomando que aún no es nativo falla con `[ERROR]: volant galaxy <subcommand> is not supported yet`, salida 1. `collection publish` y `role delete`, `search`, `import`, `setup` e `info` necesitan una cuenta de Galaxy o la base de roles del servidor, y siguen rechazados: `[ERROR]: volant galaxy <subcommand> is not supported`, salida 1.

`volant runtime install --collections` sigue instalando colecciones con el `ansible-galaxy` del runtime.
