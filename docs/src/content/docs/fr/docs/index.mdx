Volant s'adresse à celles et ceux qui exécutent des playbooks Ansible sur des hôtes Linux et veulent que ces exécutions se terminent plus vite. Il lit les playbooks, les rôles et les inventaires que vous avez déjà, dans les formats d'Ansible, et les exécute par SSH. Vous ne convertissez rien, et les mêmes fichiers continuent de fonctionner avec `ansible-playbook`.

Le nom est français : un *volant* sert à diriger. C'est avec lui que vous pilotez votre infrastructure.

<Aside type="caution" title="Pré-alpha">
Volant exécute de vrais playbooks de bout en bout, mais pas encore tous les playbooks. Essayez-le sur un hôte de test avant un hôte de production. La plupart de ce qu'il ne prend pas encore en charge est signalé avant toute connexion, et quelques manques sont silencieux : voyez [Mon playbook va-t-il s'exécuter ?](/fr/docs/start/compatibility/) pour la vérification à lancer en premier.
</Aside>

```sh
curl -fsSL https://volant.sh/install.sh | sh
volant playbook -i inventory.ini site.yml
```

[Installation](/fr/docs/start/installation/) et le [démarrage rapide](/fr/docs/start/quickstart/) prennent le relais. Vous n'avez pas besoin d'Ansible.

## Où passe le temps dans Ansible

Pour chaque tâche sur chaque hôte, `ansible-playbook` construit une charge utile de module, l'envoie par SSH et démarre un nouvel interpréteur Python sur l'hôte pour l'exécuter. Le pipelining supprime le fichier temporaire, mais chaque tâche paie toujours un nouvel interpréteur et une nouvelle série d'imports.

Volant paie ces coûts une seule fois par exécution :

- Un petit programme appelé l'agent est envoyé sur chaque hôte la première fois, puis mis en cache. Les exécutions suivantes le réutilisent.
- Le contrôleur garde une connexion SSH ouverte par hôte pendant toute l'exécution et y fait passer les tâches en flux.
- Les modules Python voyagent une seule fois vers l'hôte, dans une seule archive. Un serveur Python sur l'hôte charge le code partagé une fois et crée un processus fils pour chaque tâche.
- L'agent répond en Rust aux modules courants, comme `apt`, `systemd`, `file` et la collecte des facts, quand les arguments de la tâche le permettent, et confie tous les autres cas au module Python.

## Ce que Volant promet

Vos fichiers restent les vôtres. Volant lit le YAML d'Ansible et suit sa priorité des variables et son templating : il n'y a pas de nouveau format à apprendre.

Il s'arrête plutôt que de deviner. La plupart de ce que cette version ne prend pas encore en charge est signalé avant la première connexion, si bien qu'une exécution annonce rarement un succès après avoir sauté en silence ce que vous aviez demandé. Les [limites connues](/fr/docs/start/compatibility/#limites-connues) sont les exceptions. Cette vérification s'appelle la [vérification préalable](/fr/docs/internals/preflight/).

Il vise d'abord Linux par SSH. Le contrôleur tourne sous Linux ou macOS et pilote des hôtes Linux. Windows et les équipements réseau viendront plus tard.

## Ce que Volant laisse sur vos machines

Sur le contrôleur, la machine depuis laquelle vous lancez `volant` :

- Le script d'installation place chaque version sous `~/.local/share/volant` et lie `volant` et `volant-playbook` dans `~/.local/bin`.
- Le runtime géré est un Python 3 privé avec ansible-core. Volant le télécharge la première fois qu'une exécution a besoin de Python et n'en trouve pas d'utilisable. Il se trouve dans `~/.local/share/volant/runtime` (`~/Library/Application Support/volant/runtime` sous macOS) et occupe environ 155 MB. [Le runtime géré](/fr/docs/reference/runtime/) explique comment l'éviter ou le supprimer.
- Les caches vont sous `~/.cache/volant` : les agents qu'il envoie, et les bundles de modules Python qu'il construit.

Sur chaque hôte géré :

- L'agent en cache, un petit exécutable d'environ 1.2 MB, dans `~/.ansible/tmp/volant-agent-<version>-<uid>/`. Une tâche qui utilise `become` met en cache une seconde copie dans le répertoire personnel du compte vers lequel elle élève ses privilèges.
- Un répertoire voisin, `volant-blobs-<version>-<uid>`, contient les modules Python envoyés à l'hôte. Il existe dès qu'une exécution a utilisé un module Python.
- `~/.ansible_async` contient les fichiers d'état des tâches `async`, quand vous utilisez `async`.

Pour supprimer le cache d'un hôte, effacez les répertoires `volant-*` dans `~/.ansible/tmp` (voir [Revenir à ansible-playbook](/fr/docs/start/troubleshooting/#revenir-à-ansible-playbook)).

Volant n'envoie jamais de télémétrie. En dehors des appels que demande votre playbook, son seul usage du réseau est le téléchargement unique du runtime géré, quand une exécution en a besoin.

## Comparaison avec Ansible

Volant reproduit [ansible-core 2.19](/fr/docs/decisions/0002-ansible-core-2-19-as-reference/). Toute différence avec ansible-core est un bug, sauf si une page la présente comme un choix délibéré sous *Différences avec Ansible*.

Certaines fonctionnalités ne sont pas encore là : les plugins d'action, de callback et de vars personnalisés, ainsi que les [limites connues](/fr/docs/start/compatibility/#limites-connues). La [feuille de route](/fr/docs/project/roadmap/) dit ce qui vient ensuite.
