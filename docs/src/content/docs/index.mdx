Volant is an engine for Ansible playbooks. It reads the playbooks, roles and inventories you already have, in Ansible's own formats, and runs them against Linux hosts over SSH. You do not convert anything, and the same files keep working with `ansible-playbook`.

The name is French: a *volant* is a steering wheel. You steer your infrastructure with it.

```sh
curl -fsSL https://volant.sh/install.sh | sh
volant playbook -i inventory.ini site.yml
```

Volant is in pre-alpha: it runs real playbooks end to end, but not every playbook yet, and it names anything it does not support yet before it touches a host. [Installation](/start/installation/) and the [quickstart](/start/quickstart/) take it from here, and [Will my playbook run?](/start/compatibility/) checks an existing project in a few seconds.

## Where the time goes in Ansible

For every task on every host, `ansible-playbook` builds a module payload, sends it over SSH, and starts a fresh Python interpreter on the host to run it. Pipelining removes the temporary file, but each task still pays for a new interpreter and a new round of imports.

Volant pays those costs once per run:

- A small static agent is uploaded to each host the first time and cached there. Later runs reuse it.
- The controller keeps one SSH connection per host open for the whole run and streams tasks over it.
- Python modules travel to the host once, in a single archive. A Python server on the host loads the shared code once and forks a child for each task.
- The agent answers common modules, such as `apt`, `systemd`, `file` and fact gathering, in Rust when a task's arguments allow it, and hands every other case to the Python module.

## Measured

These numbers come from two real workloads against two Ubuntu 24.04 hosts. The first applies four published Galaxy roles, `geerlingguy.security`, `nginx`, `git` and `pip`, to hosts they have already converged. The second is the official k3s-ansible playbook against an installed cluster. Each figure is the median of three passes, measured on 2026-09-27 with `just bench` and `just bench-k3s`, and both engines ended every pass on the same recap. The reference is ansible-core 2.19.12 with `pipelining = True`.

A task that does real work still takes as long as that work. Most of Volant's time on k3s goes to restarting the k3s service, running its install script and the other commands the playbook asks for, which cost the same under either engine.

These figures describe two playbooks on two hosts. Your own numbers depend on your network latency, on what your tasks do, and on how many hosts you drive at once. The [performance page](/project/performance/) gives the full configuration, the commands that reproduce the figures, and where the time goes step by step.
</Aside>

## What Volant promises

Your files stay yours. Volant reads Ansible's YAML and follows its variable precedence and its templating, so there is no new format to learn.

It stops instead of guessing. Anything this release does not support yet is named before the first connection, so a run never reports success after quietly skipping something you asked for.

It targets Linux over SSH first. The controller runs on Linux or macOS and drives Linux hosts. Windows and network devices come later.

It collects no telemetry and makes no network call other than the ones your playbook asks for.

## How it compares to Ansible

Volant reproduces [ansible-core 2.19](/decisions/0002-ansible-core-2-19-as-reference/), which this documentation calls *the reference*. A difference from the reference is a bug, unless a page lists it as a deliberate choice under *Differences from Ansible*.

Some features are not there yet: check mode, vault, YAML inventories, the action plugins and filters of collections, and a few modules that depend on an action plugin, such as `uri` or `script`. The [roadmap](/project/roadmap/) says what comes next.
