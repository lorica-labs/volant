```sh
volant playbook [OPTIONS] <PLAYBOOK>...
volant-playbook [OPTIONS] <PLAYBOOK>...
volant --version
```

`volant playbook` takes the same options as `ansible-playbook`, for the ones that exist. `volant-playbook` is the same program under a name that reads like the one you know. Playbooks given together run in order, and each one prints its own recap.

Where an option has an `ansible.cfg` key or an environment variable, the entry names it. The option wins over both; [Configuration](/reference/configuration/) explains the order.

## Hosts and connections

<Option name="-i, --inventory, --inventory-file" arg="PATH" config="[defaults] inventory" env="ANSIBLE_INVENTORY">
  The inventory file. Only INI inventories are read, see [Inventories](/hosts/inventories/). Without one, only the implicit `localhost` exists.
</Option>

<Option name="-l, --limit" arg="SUBSET">
  Run only on hosts matching this [pattern](/hosts/inventories/#host-patterns). A limit that matches no host warns and narrows the run to what it did match.
</Option>

<Option name="--start-at-task" arg="NAME">
  Start at the first task named `NAME`; `*` and `?` match any text. The tasks in front of it are left out, `Gathering Facts` apart, and so are the plays in front of the one that holds it. Only tasks written in the play are searched, as in `ansible-playbook`: a task an `include_tasks` or `include_role` reads while the run goes is not found. A name nothing matches prints the plays with an empty recap, then an error, and exits 0.
</Option>

<Option name="--step">
  Ask before each task: `y` runs it, `n` or anything else skips it, `c` runs it and every task after it without asking. It needs a terminal; without one the run stops with exit code 250 before it touches a host.
</Option>

<Option name="--flush-cache">
  Accepted and ignored: there is no fact cache plugin yet, so there is nothing to clear.
</Option>

<Option name="--version">
  Print the Volant version and the ansible-core release it matches, then stop.
</Option>

<Option name="-u, --user" arg="REMOTE_USER" config="[defaults] remote_user" env="ANSIBLE_REMOTE_USER">
  Log in to hosts as this user. Without it, `ssh` picks the user, from your `~/.ssh/config` or your local account.
</Option>

<Option name="-c, --connection" arg="CONNECTION">
  The connection plugin for hosts that name none: `ssh` or `local`. A host's `ansible_connection` and a play, block or task `connection` keyword both win over it. Any other name fails the task with `the connection plugin '<name>' was not found`.
</Option>

<Option name="--private-key, --key-file" arg="FILE" config="[defaults] private_key_file" env="ANSIBLE_PRIVATE_KEY_FILE">
  The private key `ssh` authenticates with, passed as `ssh -i`.
</Option>

<Option name="-T, --timeout" arg="SECONDS" default="10" config="[defaults] timeout" env="ANSIBLE_TIMEOUT">
  How long to wait for a connection, passed to `ssh` as `ConnectTimeout`.
</Option>

<Option name="-f, --forks" arg="N" default="5" config="[defaults] forks" env="ANSIBLE_FORKS">
  How many hosts a play works on at once. Zero or a value that is not a number is rejected before the run starts.
</Option>

## Variables and tags

<Option name="-e, --extra-vars" arg="VARS">
  Extra variables, at the top of the [precedence order](/variables/precedence/): `key=value` pairs, inline JSON or YAML, or `@file`. Repeatable.
</Option>

<Option name="-t, --tags" arg="TAGS" config="[tags] run" env="ANSIBLE_RUN_TAGS">
  Run only tasks with these tags. Comma-separated and repeatable, and added to the configured default rather than replacing it. See [Tags and listings](/playbooks/tags/).
</Option>

<Option name="--skip-tags" arg="TAGS" config="[tags] skip" env="ANSIBLE_SKIP_TAGS">
  Skip tasks with these tags. Comma-separated and repeatable, and added to the configured default.
</Option>

## Look without running

These options read the playbooks and stop. They never connect to a host and never stop on an unsupported module, so they work on playbooks this release cannot run yet.

<Option name="--list-tasks">
  List the tasks the run would execute, in Ansible's format.
</Option>

<Option name="--list-tags">
  List the tags the run would select.
</Option>

<Option name="--list-hosts">
  List the hosts each play would run on, in inventory order.
</Option>

<Option name="--syntax-check">
  Load and compile the playbooks without running anything.
</Option>

## Privilege escalation

<Option name="-b, --become" default="false" config="[privilege_escalation] become" env="ANSIBLE_BECOME">
  Run tasks with privilege escalation. A `become` keyword in the playbook still decides for its own play, block or task. See [Privilege escalation](/hosts/become/).
</Option>

<Option name="--become-user" arg="USER" default="root" config="[privilege_escalation] become_user" env="ANSIBLE_BECOME_USER">
  The user to escalate to.
</Option>

<Option name="--become-method" arg="METHOD" default="sudo" config="[privilege_escalation] become_method" env="ANSIBLE_BECOME_METHOD">
  The escalation method: `sudo` or `su`. Other methods stop the run before it starts.
</Option>

<Option name="-k, --ask-pass">
  Ask for the SSH password on the terminal, with echo turned off. `ssh` gets it through `SSH_ASKPASS`, so it needs OpenSSH 8.4 or later. The password is in no command line, no environment sent to the host and no log. After `-k`, an empty answer to the `-K` prompt reuses the SSH password, as in `ansible-playbook`.
</Option>

<Option name="--connection-password-file, --conn-pass-file" arg="PATH">
  Read the SSH password from the first line of this file. It conflicts with `-k`.
</Option>

<Option name="--become-password-file, --become-pass-file" arg="PATH">
  Read the escalation password from the first line of this file. It conflicts with `-K`.
</Option>

<Option name="-K, --ask-become-pass">
  Ask for the escalation password on the terminal, with echo turned off. The password is written once to `sudo` and appears in no command line, log or result.
</Option>

## Vault

<Option name="-J, --ask-vault-pass">
  Ask for the vault password on the terminal, with echo turned off.
</Option>

<Option name="--vault-password-file, --vault-pass-file" arg="PATH" config="[defaults] vault_password_file" env="ANSIBLE_VAULT_PASSWORD_FILE">
  A file holding the vault password, or an executable that prints it. Repeatable.
</Option>

<Option name="--vault-id" arg="LABEL@SOURCE" config="[defaults] vault_identity_list" env="ANSIBLE_VAULT_IDENTITY_LIST">
  A vault identity: the source is a file, an executable or `prompt`. Repeatable. Every password is tried on every vaulted value, whatever its label. See [Vault](/variables/vault/).
</Option>

## Run and output

<Option name="--force-handlers" default="false" config="[defaults] force_handlers" env="ANSIBLE_FORCE_HANDLERS">
  Run notified handlers even on hosts that failed. A `force_handlers` keyword on the play takes priority. See [Handlers](/playbooks/handlers/).
</Option>

<Option name="-C, --check" default="false">
  Report what each task would change without changing it. A task's own `check_mode` keyword wins over this option, so a task with `check_mode: false` still runs for real. A host with no Python cannot answer `apt`, `user`, `group` or `file` under `--check` or `--diff`: those modules need it, and the task fails. See [Check mode and diff](/playbooks/check-and-diff/).
</Option>

<Option name="-D, --diff" default="false">
  Print the changes modules make to files, the way `ansible-playbook` does. A task's own `diff` keyword wins over this option, so `diff: false` keeps a task's changes off the screen. A host with no Python cannot answer `apt`, `user`, `group` or `file` under `--diff`: those modules need it, and the task fails. See [Check mode and diff](/playbooks/check-and-diff/).
</Option>

<Option name="-v" id="verbose">
  Show module results for successful tasks too. Repeatable, like Ansible's `-vvv`.
</Option>

<Option name="--no-color">
  Print without colors.
</Option>

<Option name="--facts" arg="auto|python|native" default="auto">
  Where gathered facts come from. `auto` uses the agent's native `setup` when every fact the plays can read is one it produces, and ansible-core's `setup` module otherwise. `python` always runs the Python module, to compare against. `native` always asks the agent's collector, and facts it does not produce are then undefined. On a host other than Debian or Ubuntu the native collector hands the task back to the Python module whatever this option says. See [Facts](/variables/facts/#native-facts).
</Option>

<Option name="--profile">
  After the recap, print on standard error where the run's time went: the controller's phases per host, then for each module the path its tasks took (`native`, `python` or `fallback`), their times, and why a native module handed a task back. The first line says where facts came from and why.
</Option>

## Environment variables

Volant reads the `ANSIBLE_*` variables named above, plus a few of its own.

<Option name="VOLANT_PYTHON" arg="PATH">
  The Python interpreter the controller uses to build module payloads. It needs `ansible-core`. When unset, Volant tries the active virtual environment, then `python3` on your `PATH`.
</Option>

<Option name="VOLANT_AGENT_DIR" arg="DIR">
  A directory that holds the agent binaries. It is checked first, before the agents built into the release controller and the directory of the `volant` executable. Useful with a controller built from source, or to test an agent of your own.
</Option>

<Option name="VOLANT_BATCHING" arg="1" config="[volant] batching">
  Turns on [cross-host batching](/hosts/batching/).
</Option>

<Option name="VOLANT_NATIVE_MODULES" arg="0" config="[volant] native_modules">
  With `0`, every task runs ansible-core's Python module instead of the agent's native version. See [Native modules](/internals/python/#native-modules).
</Option>

<Option name="VOLANT_SSH_CONTROL_MASTER" arg="0" config="[volant] ssh_control_master">
  With `0`, every `ssh` run opens its own connection instead of sharing one per inventory host.
</Option>

<Option name="VOLANT_PROFILE_JSON" arg="FILE">
  Write the run's profile to this file, one JSON object per line: the native modules each agent reported, then the phases, then one line per task with its module, path, hand-back reason and times in microseconds. It is written whatever became of the run, and a file that cannot be written only prints a warning.
</Option>

## Not there yet

Every `ansible-playbook` option is accepted. `--scp-extra-args` and `--sftp-extra-args` have no effect, because files move over the agent link. The [parity page](/reference/parity/#ansible-playbook-option) lists the rest.
