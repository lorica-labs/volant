Volant reads the same `ansible.cfg` as `ansible-playbook`, and stops at the first file it finds:

<Steps>

1. the file named by `ANSIBLE_CONFIG`
2. `./ansible.cfg`
3. `~/.ansible.cfg`
4. `/etc/ansible/ansible.cfg`

</Steps>

Volant skips `./ansible.cfg` when the working directory is writable by other users (mode bit `o+w`), as `ansible-playbook` does. Another local user could have put the file there. The sticky bit and the owner of the directory change nothing. Volant prints `[WARNING]: Ansible is being run in a world writable directory (...), ignoring it as an ansible.cfg source.` on standard error and continues with the next file. A file named by `ANSIBLE_CONFIG` is read whatever the mode of the working directory.

For each setting, the environment variable beats the file, and the command-line option beats both. Keys Volant does not use are ignored, as Ansible ignores the ones it does not use.

A file that exists but cannot be read is skipped, and the run continues with the defaults. Volant prints a warning first, which Ansible does not: a file you wrote that the process cannot open deserves a line, and a warning does not change the exit code.

## [defaults]

<Option name="inventory" id="defaults-inventory" flag="-i" env="ANSIBLE_INVENTORY">
  The inventory sources, as a comma-separated list. See [Inventories](/hosts/inventories/#sources).
</Option>

<Option name="timeout" id="defaults-timeout" default="10" flag="-T" env="ANSIBLE_TIMEOUT">
  Seconds to wait for a connection. It becomes `ConnectTimeout` on the `ssh` command line.
</Option>

<Option name="remote_user" id="defaults-remote-user" flag="-u" env="ANSIBLE_REMOTE_USER">
  The user to log in as. Without it, `ssh` picks one.
</Option>

<Option name="private_key_file" id="defaults-private-key-file" flag="--private-key" env="ANSIBLE_PRIVATE_KEY_FILE">
  The private key `ssh` authenticates with.
</Option>

<Option name="host_key_checking" id="defaults-host-key-checking" default="true" env="ANSIBLE_HOST_KEY_CHECKING">
  With it on, an unknown host key makes the host unreachable. With it off, Volant adds `StrictHostKeyChecking=no` and `UserKnownHostsFile=/dev/null`, so an unknown key is accepted and not recorded.
</Option>

<Option name="remote_tmp" id="defaults-remote-tmp" default="~/.ansible/tmp" env="ANSIBLE_REMOTE_TMP">
  The directory on each host that holds the [agent cache](/hosts/connections/#the-agent-cache).
</Option>

<Option name="forks" id="defaults-forks" default="5" flag="-f" env="ANSIBLE_FORKS">
  How many hosts a play works on at once. Zero or a value that is not a number is rejected before the run starts. Playbooks read the current value as `ansible_forks`.
</Option>

<Option name="async_dir" id="defaults-async-dir" default="~/.ansible_async" env="ANSIBLE_ASYNC_DIR">
  The directory on each host that holds the status files of [async tasks](/playbooks/how-a-play-runs/#async-tasks). `ansible_async_dir` overrides it.
</Option>

<Option name="enable_task_debugger" id="defaults-enable-task-debugger" default="false" env="ANSIBLE_ENABLE_TASK_DEBUGGER">
  Open the [debugger](/playbooks/how-a-play-runs/#other-strategies) after every failed or unreachable task.
</Option>

<Option name="show_task_path_on_failure" id="defaults-show-task-path-on-failure" default="false" env="ANSIBLE_SHOW_TASK_PATH_ON_FAILURE">
  Print `task path: <file>:<line>` before the `fatal:` line of a failed task. From `-vv` the line already follows every task banner, so this changes nothing there. A loop item's `failed:` line and an unreachable host get no path line. As in Ansible, `y`, `yes`, `on`, `true`, `t` and `1` turn it on in any case, and any other word, an empty variable included, leaves it off.
</Option>

<Option name="localhost_warning" id="defaults-localhost-warning" default="true" env="ANSIBLE_LOCALHOST_WARNING">
  Warn when the inventory holds no host, so that only the implicit `localhost` is left. `all` does not match that host.
</Option>

<Option name="force_handlers" id="defaults-force-handlers" default="false" flag="--force-handlers" env="ANSIBLE_FORCE_HANDLERS">
  Run notified handlers even on hosts that failed.
</Option>

<Option name="roles_path" id="defaults-roles-path" default="~/.ansible/roles:/usr/share/ansible/roles:/etc/ansible/roles" env="ANSIBLE_ROLES_PATH">
  Where roles are looked for, after `<playbook_dir>/roles` and before `<playbook_dir>` itself. See [Roles](/playbooks/roles/#finding-a-role).
</Option>

<Option name="collections_path" id="defaults-collections-path" default="~/.ansible/collections:/usr/share/ansible/collections" env="ANSIBLE_COLLECTIONS_PATH">
  Where a three-part role name such as `acme.demo.hello` is looked for. A collection's modules are found by the controller's ansible-core, in the paths it is configured with: see [Modules from collections](/internals/python/#modules-from-collections).
</Option>

<Option name="gathering" id="defaults-gathering" default="implicit" env="ANSIBLE_GATHERING">
  `implicit`, `explicit` or `smart`. See [The fact cache](/hosts/fact-cache/#gathering).
</Option>

<Option name="fact_caching" id="defaults-fact-caching" default="memory" env="ANSIBLE_CACHE_PLUGIN">
  `memory` keeps facts for the run, `jsonfile` keeps them between runs. See [The fact cache](/hosts/fact-cache/).
</Option>

<Option name="fact_caching_connection" id="defaults-fact-caching-connection" env="ANSIBLE_CACHE_PLUGIN_CONNECTION">
  The directory of the `jsonfile` cache.
</Option>

<Option name="fact_caching_timeout" id="defaults-fact-caching-timeout" default="86400" env="ANSIBLE_CACHE_PLUGIN_TIMEOUT">
  Seconds a cached entry stays fresh. `0` never expires.
</Option>

<Option name="fact_caching_prefix" id="defaults-fact-caching-prefix" env="ANSIBLE_CACHE_PLUGIN_PREFIX">
  Put in front of each cache file name.
</Option>

## [privilege_escalation]

<Option name="become" id="privilege-escalation-become" default="false" flag="-b" env="ANSIBLE_BECOME">
  Escalate by default. Playbook keywords and host variables take priority, see [Privilege escalation](/hosts/become/#which-setting-wins).
</Option>

<Option name="become_user" id="privilege-escalation-become-user" default="root" flag="--become-user" env="ANSIBLE_BECOME_USER">
  The user to escalate to.
</Option>

<Option name="become_method" id="privilege-escalation-become-method" default="sudo" flag="--become-method" env="ANSIBLE_BECOME_METHOD">
  The escalation method: `sudo` or `su`. `su` needs an `ssh` connection, because it reads its password from a terminal.
</Option>

<Option name="become_exe" id="privilege-escalation-become-exe" env="ANSIBLE_BECOME_EXE">
  The program to run instead of `sudo` or `su`.
</Option>

<Option name="become_flags" id="privilege-escalation-become-flags" env="ANSIBLE_BECOME_FLAGS">
  The flags given to that program, in place of `-H` for `sudo` and of none for `su`. A blank value gives no flags at all.
</Option>

## [volant]

Ansible ignores this section, so one `ansible.cfg` can carry it and still drive both engines. `ansible-config validate` is the exception, see [Cross-host batching](/hosts/batching/#turning-it-on).

<Option name="batching" id="volant-batching" default="false" env="VOLANT_BATCHING">
  Off by default. With `batching = true`, a host moves on to its next tasks without waiting for the other hosts, except in front of a task whose text reads another host (`hostvars`, `ansible_play_hosts`, `delegate_to`, a template or variable that does). A dependency the playbook does not spell, such as a service another host is still installing or a file on a host named literally, is not waited for. Turn it on only for plays whose hosts do not depend on each other that way. See [Cross-host batching](/hosts/batching/).
</Option>

<Option name="native_modules" id="volant-native-modules" default="true" env="VOLANT_NATIVE_MODULES">
  Let the agent answer a task with its native version of the module, when the task's arguments stay within what that version implements. With `false`, every task goes to ansible-core's Python module, and `setup` too, which is how to compare the two paths on a real run. The value is read as ansible-core reads a boolean, and a word it does not know stops the run with exit code 5. See [Native modules](/internals/python/#native-modules).
</Option>

<Option name="runtime" id="volant-runtime" default="auto" env="VOLANT_RUNTIME">
  Where the controller's Python comes from. `auto` uses `VOLANT_PYTHON`, then the managed runtime when installed, then the active virtual environment and `python3`, and installs the managed runtime when none of them works. `managed` uses `VOLANT_PYTHON` or the managed runtime only, and installs it when it is missing. `system` never uses or installs the managed runtime. Any other word stops the run with exit code 5. See [The managed runtime](/reference/runtime/).
</Option>

<Option name="ssh_control_master" id="volant-ssh-control-master" default="true" env="VOLANT_SSH_CONTROL_MASTER">
  Share one OpenSSH connection between all the `ssh` runs of an inventory host. With `false`, each link and probe opens its own connection. See [One connection per host](/hosts/connections/#one-connection-per-host).
</Option>

<Option name="host_named_paths" id="volant-host-named-paths" default="allow" env="VOLANT_HOST_NAMED_PATHS">
  What `template`, `copy`, `script`, `unarchive` and `assemble` do with a controller `src` that a managed host named, through a gathered fact or a registered result. `allow` reads the file as ansible-core does: a managed host can choose which readable controller file a task sends to it. `contained` reads it only when the file is in the `files` or `templates` directory of the role, the playbook or the task's own directory, and fails the task for any other name. Key names are matched exactly and a key Volant does not know is ignored, as in the rest of this section, so a misspelled `host_named_paths` leaves the default `allow`. `refuse` fails the task for every such name. Any other word stops the run with exit code 5. A `fetch` whose `dest` a host named is written under `allow`, as ansible-core writes it. Under `contained` and `refuse` it is written only inside the directories of `host_named_dest_dirs`, and none when that key is unset: see `host_named_dest_dirs`. See [A source file a managed host named](/reference/action-plugins/#a-source-file-a-managed-host-named).
</Option>

<Option name="host_named_dest_dirs" id="volant-host-named-dest-dirs" default="unset" env="VOLANT_HOST_NAMED_DEST_DIRS">
  A colon-separated list of absolute controller directories under which `fetch` writes when a managed host named its `dest`, through a registered result or a fact. Unset, the default, `fetch` writes such a `dest` as ansible-core does, unless `host_named_paths` is `contained` or `refuse`. Set, the list limits every such `dest`, and an empty value refuses them all. Each entry must be absolute, with no `~` and no `..`, and must not be `/`; anything else stops the run with exit code 5 and names the key, the value and the entry. A `dest` that the playbook wrote is not held to the list. See [A dest a managed host named](/reference/action-plugins/#a-dest-a-managed-host-named).
</Option>
