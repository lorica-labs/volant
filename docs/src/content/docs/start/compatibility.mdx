Volant loads the whole ansible-core 2.19 grammar, so your playbook parses here as it parses under Ansible. Most of what this release does not support yet is named before the first connection, and the run stops there. You find out in seconds. The [known gaps](#known-gaps) below are the exceptions: a run can ignore a setting or give a wrong result there without an error.

## Check a project

<Steps>

1. Read it without running it. Listings and `--syntax-check` never stop on an unsupported module or keyword, so they work even on a playbook this release cannot run yet:

   ```sh
   volant playbook -i inventory.ini site.yml --syntax-check
   volant playbook -i inventory.ini site.yml --list-tasks
   ```

   If the task list matches what `ansible-playbook --list-tasks` prints, Volant compiled your roles, imports and tags the same way.

2. Ask for a real run against one host you can afford to touch:

   ```sh
   volant playbook -i inventory.ini site.yml --limit test1
   ```

   Most of what this release cannot execute stops the run before it connects. The message names the module, the keyword or the value, and the run exits with code 4.

3. Fix or wait. What is not supported yet is listed in [Keywords](/reference/keywords/), [Modules](/reference/modules/) and the [known gaps](#known-gaps) below, and most have a workaround.

</Steps>

<Aside type="note">
A file that only a dynamic `include_tasks` or `include_role` names is read when a host reaches that statement, so an unsupported module or keyword inside it stops the run at that point instead of before it. See [Includes and imports](/playbooks/includes/).
</Aside>

| Blocks | `block`, `rescue`, `always` | |
| Reuse | roles and dependencies, `import_tasks`, `import_role`, `import_playbook`, `include_tasks`, `include_role`, `include_vars` | |
| Delegation | `delegate_to`, `delegate_facts`, `local_action`, `run_once` | |
| Modules | `command`, `shell`, `raw`, controller modules, `copy`, `dnf`, `yum`, `fetch`, `package`, `reboot`, `service`, `template`, `unarchive`, `uri`, `script`, most ansible-core Python modules, modules from installed collections and their action plugins | a collection's action plugin that needs Windows or a network device, custom action plugins |

## Common blockers and what to do

| Not supported yet | Why | What you can do today |
|---|---|---|
| An action plugin of your own, in `action_plugins/` | Volant runs the action plugins of ansible-core and of installed collections, not yours. | Write a module, or keep the play under `ansible-playbook`. |
| A collection that is not installed | Volant does not install one during a run. It asks the controller's ansible-core what is installed, before the first connection. | Run `volant runtime install --collections NAME`, or the `ansible-galaxy collection install` command the error names. See [The managed runtime](/reference/runtime/#collections) and [Modules from collections](/internals/python/#modules-from-collections). |
| No Python with ansible-core on the controller | Volant installs its own on first need, with `curl` or `wget` and `tar`. | Nothing, or `volant runtime install` ahead of time. Without a network, use `volant runtime pack` and `install --from`. |
| `apt`, `user`, `group` or `file` under `--check` or `--diff` on a host with no Python | These modules answer through Python on the host when the run asks for a check or a diff. | Install Python on the host, or run the play without `--check` and `--diff`. |
| `!!binary`, a duplicate anchor, or a date or a set as a typed value | The value model has no bytes, no date and no set. A date loads as its ISO text, a `!!set`, `!!omap` or `!!pairs` as the mapping or list it is written as. `!!binary` stops the load, and a second `&anchor` of the same name is accepted. | Write the value as a plain string, list or mapping, and give each anchor its own name. |
| Arithmetic on an integer wider than 128 bits | A module can return such an integer, such as the modulus of an RSA key. Volant keeps every digit in results, variables, `string`, `to_json` and `from_json`, and compares a wide integer with any number by value, in the comparison operators, `min`, `max`, `sort`, `unique` and `list.sort()`. The operators `+`, `-`, `*`, `/`, `//`, `%` and `**` and the `abs` and `round` filters refuse a wide operand, and a result wider than 128 bits is an error. A YAML integer of more than 4300 digits is refused, and so is a text of that size given to `int` (the filter answers its default), as Python 3.11 and later do. Python reads a text of more than 4300 digits exactly in base 2, 4, 8, 16 or 32, and `int` answers its default for it. | Do the arithmetic in a module or in `command` with `python3 -c`, and keep the wide value as text. |

## Known gaps

These differ from `ansible-playbook` without a message before the run, or with a message that names something else. Each row says what happens.

| What | What happens |
|---|---|
| `callback_plugins/`, `vars_plugins/`, `stdout_callback`, `callbacks_enabled`, `result_format` | Ignored. The output is the default one. |
| `volant check`, `inventory`, `vault`, `doc`, `config`, `galaxy` and ad-hoc commands | They do not exist. `volant` has `playbook` and `runtime`. |
| A comparison written between two literals of types Python cannot order, such as `{{ 'a' < 1 }}` | It answers `false` or `true` where ansible-core fails with `'<' not supported between instances of 'str' and 'int'`. The template engine works out a comparison of literals before Volant sees it. With a variable on either side the comparison fails as in ansible-core. |
| A task with `no_log: true` that fails | On purpose. Volant prints `[ERROR]: Task failed: Action failed: <error censored due to no log>` and nothing else of the cause. ansible-core 2.19.12 prints the cause: `[ERROR]: Task failed: Action failed: <the msg of fail or assert>`, the error of the module, and the `<<< caused by >>>` blocks. That text can hold a secret, such as the `msg` of a `fail` that names a password. The [security policy](https://github.com/lorica-labs/volant/blob/main/SECURITY.md) counts a secret that reaches a log or a terminal where `no_log` hides it in ansible-core as a vulnerability, so Volant hides it. The `fatal:` line, the registered result and the recap are the same in both. To read the cause, run the task without `no_log`. |
| SIGTERM | On purpose. Volant stops cleanly: it cancels the running tasks, removes the directory that holds the connection password, prints the recap, and exits with code 99, as it does for Ctrl-C. `ansible-playbook` does not catch SIGTERM. It dies at once with code 143 and prints no recap. Measured with `kill -TERM` during a `command: sleep`: 99 under Volant, 143 under ansible-core 2.19.12. |

[Templating](/variables/templating/#not-there-yet) lists the filters and arguments that fail. The [parity page](/reference/parity/) marks a filter `partial` when one of its arguments fails.

If a playbook behaves differently under Volant and `ansible-playbook` without being reported as unsupported, that is a bug. Please [open a compatibility report](https://github.com/lorica-labs/volant/issues/new?template=compat.yml) with a minimal playbook.
