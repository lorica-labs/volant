## Install

```sh
curl -fsSL https://volant.sh/install.sh | sh
```

The script works on Linux and macOS, on x86_64 and arm64. On Linux it takes the static build. It downloads the newest release for your machine, checks its SHA-256 checksum, unpacks it under `~/.local/share/volant`, and links `volant` and `volant-playbook` into `~/.local/bin`. It asks for no root access and changes nothing outside those two directories. You can [read it](https://volant.sh/install.sh) before you run it.

Check that it worked:

```sh
volant --version
```

If your shell cannot find `volant`, add `~/.local/bin` to your `PATH`. The script prints the line to add when it is missing.

### Options

The script reads three environment variables:

| Variable | Default | What it changes |
|---|---|---|
| `VOLANT_VERSION` | the newest release | The release to install, such as `v0.1.0-alpha.7`. |
| `VOLANT_HOME` | `~/.local/share/volant` | Where releases are unpacked. |
| `VOLANT_BIN_DIR` | `~/.local/bin` | Where the `volant` and `volant-playbook` links go. |

```sh
curl -fsSL https://volant.sh/install.sh | VOLANT_VERSION=v0.1.0-alpha.7 sh
```

## What you get

One binary. The release `volant` carries the agents it uploads to your hosts, so there is nothing else to install and nothing to keep next to it:

| File | What it is |
|---|---|
| `volant` | The controller, the command you run. |
| `volant-playbook` | The same controller under a name that reads like `ansible-playbook`. |

On first use, the controller writes its agents to `~/.cache/volant/agents/<version>/`, or under `$XDG_CACHE_HOME` when it is set: the agent for your own machine, used by `ansible_connection=local`, and the ones it uploads to x86_64 and arm64 Linux hosts. Later runs reuse them, and a copy that does not match the agent built into the controller is written again.

## Builds and platforms

Every release has one archive per platform. Linux has two, a static build and a glibc build. macOS has one, because macOS does not let a program link without its system libraries.

| Platform | Archive | Linkage | Minimum | Needs beside it |
|---|---|---|---|---|
| Linux x86_64, static | `volant-x86_64-unknown-linux-musl.tar.xz` | Static. No libc. | Any Linux | `ssh` client, Python for Python modules |
| Linux x86_64, glibc | `volant-x86_64-unknown-linux-gnu.tar.xz` | Dynamic, glibc only | glibc 2.17 | `ssh` client, Python for Python modules |
| Linux arm64, static | `volant-aarch64-unknown-linux-musl.tar.xz` | Static. No libc. | Any Linux | `ssh` client, Python for Python modules |
| Linux arm64, glibc | `volant-aarch64-unknown-linux-gnu.tar.xz` | Dynamic, glibc only | glibc 2.17 | `ssh` client, Python for Python modules |
| macOS, Apple silicon | `volant-aarch64-apple-darwin.tar.xz` | Dynamic, system libraries only | macOS 11 | `ssh` client, Python for Python modules |
| macOS, Intel | `volant-x86_64-apple-darwin.tar.xz` | Dynamic, system libraries only | macOS 10.12 | `ssh` client, Python for Python modules |

Both Linux builds run the same code and carry the same agents. The static build runs on any distribution, on Alpine, and in a container with no libc. The glibc build runs on glibc 2.17 or newer, which covers Debian 8, Ubuntu 14.04, RHEL and CentOS 7 and everything after them, and it takes the security updates of the system libc. The release process checks both builds on the files before it publishes them: a static build has no library dependency, a glibc build needs no symbol above glibc 2.17, and a macOS build links only libraries under `/usr/lib` and `/System/Library`.

The install script always takes the static build on Linux. The `volant-installer.sh` file of a release takes the glibc build on a glibc 2.17 host or newer, and the static build on any other Linux, such as Alpine. `cargo binstall` takes the glibc build on any glibc host without reading its version, and the static build on Alpine. On a glibc host older than 2.17, download the static archive by hand.

### In a container

The static build needs nothing from the image, so it runs in a container built `FROM scratch`:

```dockerfile
FROM scratch
COPY volant /volant
ENTRYPOINT ["/volant"]
```

A scratch image has no `ssh`, no Python, no shell and no `/etc/passwd`. With only the controller in it, a playbook can run on `connection: local` and use `command` with `argv`. SSH connections need an `ssh` client in the image, Python modules and fact gathering need Python, and `shell` and `raw` need a shell. The controller keeps the agent it extracts under `~/.cache/volant`, or under `$XDG_CACHE_HOME` when it is set: give it a directory it can write.

## What the machines need

<Tabs>
  <TabItem label="Controller">
    - Linux or macOS.
    - The OpenSSH client on your `PATH`. Volant runs `ssh` itself, so your `~/.ssh/config` applies.
    - `curl` or `wget`, and `tar`, the first time a playbook needs Python.

    Ansible is not needed. For Python modules and fact gathering, Volant uses a Python 3 with `ansible-core`. When it finds none, it downloads its own, checks every file against a pinned hash and keeps it under `~/.local/share/volant/runtime`. A run that does this prints one line, and the install takes about 8 seconds. If you already have such a Python, Volant uses `VOLANT_PYTHON` first, then its own runtime, then the active virtual environment, then `python3` on your `PATH`. See [The managed runtime](/reference/runtime/). It has not been tested on macOS.

    A playbook made only of `command`, `shell`, `raw` and controller-side modules, with `gather_facts: false`, needs no Python at all.
  </TabItem>
  <TabItem label="Managed hosts">
    - Linux, x86_64 or arm64.
    - An SSH server and an account you can log into with a key or an ssh-agent.
    - A Python 3 interpreter for Python modules and fact gathering. The host does not need ansible-core: Volant sends every file a module imports.
    - `sudo` if you use `become`.

    Nothing has to be installed by hand. The controller uploads the agent with the first task and caches it under `~/.ansible/tmp`.
  </TabItem>
</Tabs>

## Update

Run the install command again. It installs the newest release next to the ones you have and points the links at it. Older releases stay under `~/.local/share/volant`, so going back is a matter of setting `VOLANT_VERSION`.

## Other ways to install

<Tabs>
  <TabItem label="cargo binstall">
    ```sh
    # Only pre-releases exist so far, so name the version.
    cargo binstall volant@0.1.0-alpha.7
    ```

    This downloads a release binary with its agents included. On a glibc host it is the glibc build, on Alpine the static build.
  </TabItem>
  <TabItem label="Manual download">
    Every release on the [releases page](https://github.com/lorica-labs/volant/releases) has one archive per platform, named `volant-<target>.tar.xz` as in the table above, with a `.sha256` file next to it. Unpack it and put `volant` on your `PATH`:

    ```sh
    tar -xJf volant-x86_64-unknown-linux-musl.tar.xz
    install -m 755 volant-x86_64-unknown-linux-musl/volant ~/.local/bin/volant
    ```
  </TabItem>
  <TabItem label="From source">
    ```sh
    cargo install --git https://github.com/lorica-labs/volant volant
    ```

    A build from source does not carry the agents, because they are cross-compiled for the hosts. Point `VOLANT_AGENT_DIR` at a directory that holds them, or build them from a checkout: `cargo build` leaves a local agent next to the controller, and `just agent-musl` builds the x86_64 Linux one. `just smoke-embedded` shows how a release build embeds them.
  </TabItem>
</Tabs>

## Uninstall

Remove the release directory, the links and the controller's agent cache. On each host, the agent cache is one directory per account the run acted as:

```sh
volant runtime remove --all
rm -rf ~/.local/share/volant ~/.local/bin/volant ~/.local/bin/volant-playbook ~/.cache/volant
ssh web1 'rm -rf ~/.ansible/tmp/volant-agent-*'
```
