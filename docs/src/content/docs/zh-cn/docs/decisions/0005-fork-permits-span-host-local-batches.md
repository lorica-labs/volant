## 背景

主机驱动在打开连接之前，会取走 `forks` 个许可中的一个，并在它收集的批次得到应答后归还。[ADR 0004](/zh-cn/docs/decisions/0004-become-runs-a-second-agent-under-sudo/) 让活动的 agent 连接数没有上限；把提权链路与许可绑定在一起，才给了它们上限，因为这样 `forks` 既限制了正在工作的主机，也限制了打开的连接。二十台主机在 `ulimit -n 128` 和 `-f 5` 下提权到 root，以前会为一台完全可达的主机报告 `Too many open files`。

每个批次都交还链路并不是没有代价的，而一个批次结束的次数也比这个词所暗示的更多。下面任何一种情况都会关闭一个批次：带有 `register`、`loop`、`changed_when` 或 `failed_when` 的 task；读取另一台主机状态的 task，它是在自己前面的一道边界；以及提权到不同用户的 task。register 一个结果是很平常的事，所以一个有六个提权 task、每个都带 `register` 的 play，要付出六次提权，每次都是一次 `sudo` 探测加一次启动 agent 的 `sudo`。在开发机上用一个会记录自己被要求运行什么的 `sudo` 测量：这六个 task 有十二次调用。

`register` 并不需要另一台主机，所以许可是在一个并不存在的等待之前被还回去的。

## 决策

驱动在即将继续执行自己的下一个步骤时，会从一个批次到下一个批次一直持有它的 fork 许可和提权链路。它会在每次等待其他主机之前、以及 play 结束时归还二者，在 play 结束时再持有它们只会占着描述符。因失败而退出运行的驱动也会归还它们。

有四种步骤算作等待：关键字表声明为同步点的步骤，其文本指向另一台主机状态的步骤，步骤列表在此增长的拼接点，以及后继位于其中一个之后的步骤。一个要等到自己的结果决定主机去向才放行的步骤也算。

提权链路仍然像以前那样在 task 之外关闭，而不是等待：`shutdown` 给它的 agent 最多两秒，而驱动在批次之间付出这个时间，会让刚刚因释放许可而空出来的东西重新串行化。

这个决策没有增加任何连接复用。每条链路仍然是它自己的 `ssh` 进程。

## 后果

- 活动链路的上限是：每台主机一条，即比 play 存活得更久的那个连接，加上 `forks` 乘以一个驱动在持有一个许可期间提权到的不同目标用户的数量。早先的上限为每个驱动计一条提权链路，因为每个批次会关闭自己的那条；现在同一个许可下的多个连续批次可以指名不同的用户。
- 实测，二十台主机在 `-f 5` 下提权到 root：控制节点的峰值是 84 个打开的描述符，之前的峰值是 69，限制是 128。运行以 0 退出，没有不可达的主机，早先的上限正是凭这同一个证明被接受的。
- 一个有六个提权 task、每个都以 `register` 结束批次的 play，现在启动一个提权 agent，而不是六个。
- 主机在等待处轮流，而不是在每个批次轮流。当 `forks` 小于存活主机数，且 play 的所有步骤都是主机本地的时，一台主机现在会先运行完它剩下的步骤，下一台才开始，而以前两者是交替的。工作是一样的，汇总也一样；变化的是行到达的顺序，而在没有东西同步的两台主机之间，这个顺序本来就是无序的。
- 从不提权的 play 除了持有许可稍久一点之外不受影响，每个 task 都跨主机读取的 play 则像以前一样在每一步都归还许可。

取代 [ADR 0004](/zh-cn/docs/decisions/0004-become-runs-a-second-agent-under-sudo/) 中“每台主机的活动 agent 连接数没有上限”这条后果。

## 状态

自 2026-09-20 起，只有在操作者提出要求时，驱动才会让许可越过一个主机本地步骤。`ansible.cfg` 中的 `[volant] batching = true`，或 `VOLANT_BATCHING=1`，会开启这个决策；没有它，每个步骤都是一次等待，正如 `linear` 所说的那样。

原因是上面的第四条后果。哪些步骤算等待，是从 task 的文本读出来的，而经过文件、数据库或服务的依赖不会留下可读的文本。Ansible 的 `linear` 承诺主机会在每个 task 之前汇合，按这个承诺写出的 playbook 有权依赖它。仅凭文本就另作决定，对一个首要承诺是 playbook 原样运行的引擎来说，是错误的默认。

决策描述的一切都保留下来，并且仍在该选项之下运行。两种设置的实测开销，以及默认值无论如何都保留的内容，见[跨主机批处理](/zh-cn/docs/hosts/batching/)。

## 更新，2026-10-24

上面的第一条后果不再成立。自 2026-09-22 起（[#178](https://github.com/lorica-labs/volant/pull/178)），主机会让它的提权链路越过同步点保留下来，并且它持有自己的链路外加至多一条提权链路，无论不同目标用户有多少个。与手头链路提权方式不同的批次（另一个用户、另一个提权程序或标志、另一种传输）会关闭旧链路并打开新链路。许可本身仍如这里所决定的，在每次等待之前归还。当前的规则见[连接与 become](/zh-cn/docs/hosts/connections/#持久连接)。
