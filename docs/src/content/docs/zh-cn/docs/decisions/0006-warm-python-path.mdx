## 背景

Python 路径必须在不在受管主机上安装 ansible-core 的前提下运行 ansible-core 的模块。每个 task 一个进程要花 340 毫秒。从一个什么都没加载的 Python 服务 fork，要花 266 毫秒，这不足以证明这套机制的合理性。

从一个模块的 zip 中加载 `module_utils` 再 fork，要花 12.8 毫秒，但这会把 Python 的 `ansible` 包钉在那一个 zip 上。之后其他每个模块都会导入失败。这是实测过的，而且它是明显地失败，而不是悄悄地失败。

不同模块 zip 之间共用的条目是逐字节相同的：十个模块的 146 个条目零冲突。把它们合并成一个 zip 是定义明确的，构建器把冲突视为硬错误。

## 决策

每次运行构建一个 union blob，而不是每个模块一个 blob。这个 blob 包含每个模块及其导入的 `module_utils`，以其内容的 BLAKE3 哈希标识，并缓存在受管主机上。Python 服务只加载它一次，并为每个 task fork 一个子进程。

五个 golden 模块的 union blob 恰好是 631050 字节，而分开的 zip 是 2307982 字节。节省了 72.7%。预加载的 fork 路径每个 task 花 12.8 毫秒，加载 blob 在每个服务上花一次 264.5 毫秒。

## 后果

- 一次运行得到一套一致的 `module_utils`，所以模块不会从互不兼容的 zip 中导入。
- 构建器遇到相互冲突的共享条目必须停止，而不是选一个版本。
- 受管主机在使用 blob 之前先缓存并校验它。
- 控制节点需要 ansible-core；受管主机不需要。

## 在真实 play 上的测量

上面的数字来自循环中的单个模块。2026-09-21 针对一台受管主机运行的三十五个 task 的 playbook，说明了这些数字对一个真实 play 的价值。它安装包、创建目录、逐行写入配置、读回文件，并让一个服务保持启动，而且它会提权，因为这样的 play 就是这么做的。

Volant 现在运行这个 play 所用的时间，是启用 pipelining 的参照版本的 40%。一遍运行在主机上打开 3 个 ssh 会话，而不是 58 个。修复之前的那一组复现了第一张表，误差在百分之一以内，所以收益来自修复，而不是机器的变化。

每个 task 的平均值里仍然包含真实的工作。`apt` 花约 755 毫秒与 `dpkg` 交互，而收集 facts 是这个 play 中最昂贵的 task。预热路径去掉的是模块周围的开销，而不是模块自己的工作。

保持链路是有代价的。许可带着链路一起走的时候，`forks` 也限制了一次运行持有多少个提权连接。现在一次运行可以为每台主机持有两条链路，按每条链路三个文件描述符算，限制在 1024 个描述符的控制节点，会在约 169 台提权主机处触顶，而不是约 330 台。

## 更新，2026-10-24

上面的测量止于第一个结果，那是一次失利：Volant 用了 30.2 秒，而启用 pipelining 的参照版本是 20.02 秒。不提权的二十一个 task，Volant 每个花 17 毫秒，参照版本是 437 毫秒，所以预热路径是有效的。同样的 task 在 `become: true` 之下，每个花 897 毫秒，参照版本是 464 毫秒。到达同步点的主机，会在同一步里归还它的 fork 许可并关闭它的提权链路，而一个全是 Python task 的 play 几乎每个 task 都会到达一个同步点，于是每个提权 task 都要付出一个新的 `ssh` 会话、一次新的 `sudo` 和一次新的握手。一次运行在主机上打开了 44 个会话，而不提权的运行打开 4 个。

修复（[#178](https://github.com/lorica-labs/volant/pull/178)，2026-09-22）让提权链路越过同步点保留下来，只归还另一台主机正在等待的许可。在同一台主机上用同样的方法再次测量：

| 运行 | 总耗时 | 每个 task |
|---|---|---|
| Volant，在每个点关闭链路 | 30.51 秒 | 872 毫秒 |
| Volant，保持链路 | 7.90 秒 | 226 毫秒 |
| ansible-core，`pipelining = True` | 19.72 秒 | 564 毫秒 |

Volant 随后运行这个 play 所用的时间，是启用 pipelining 的参照版本的 40%，一遍运行在主机上打开 3 个 `ssh` 会话，而不是 58 个。第一行与第一次测量吻合，误差在百分之一以内，所以收益来自修复，而不是机器的变化。
